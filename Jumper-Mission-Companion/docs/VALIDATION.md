## Remaining acceptance on your laptop

1. Run setup and the native dashboard on Windows; verify its own OpenGL rendering and the supplied Windows controller extension load correctly.
2. Enable the camera yourself. Check each gesture with both hands, several distances and normal room lighting; confirm no unintended turns and prompt tracking-loss handling. Do not call this production-quality recognition until these observations support it.
3. Enable the microphone yourself. Check supported commands with your accent, background noise and the actual browser speech service. If unsupported, the UI explains that and typed commands remain available.
4. Confirm performance while moving between panels and switching activities; leave the page and verify robot motion stops. Version 1.1.0 preserves a running focus timer quietly; a long host-loop stall cancels motion rather than replaying stale actions after wake.
5. Physical robot deployment, real sensors, unknown-map perception/SLAM, custom trained policies, simulator-to-hardware transfer and BE UNLIMITED native `.app` packaging have **not** been implemented or certified here.

The project is a tested local simulation build with device-dependent checks remaining. It must not be described as perfect, hardware tested, or fully competition ready.

## Windows connection-abort handling — version 0.1.3

A user screenshot showed ConnectionAbortedError WinError 10053 while flushing HTTP response headers. Because header output was outside the transport exception handler, the POST handler misclassified a browser disconnect as a robot fault and then failed while sending the error response. Response headers and bodies now share a transport exception boundary; POST success transmission is outside the simulation-error boundary, and aborted request reads are contained separately.

45 unit tests passed, including four new HTTP regressions. An injected ConnectionAbortedError(10053) during a real command response does not set engine.fault, does not emit a traceback, and the next command succeeds. This reproduces the exception path on Linux; actual Windows execution and the original cause of the connection abort remain unverified.

## 1.3.0 — Render package and optional Netlify frontend

The separate hosted WSGI entrypoint runs behind Gunicorn, binds Render's PORT on 0.0.0.0, validates exact public origins, and uses random HttpOnly/SameSite cookies with distinct per-session command tokens. Each active visitor has an independent engine, physics model and task history. Session capacity, idle expiry, maximum lifetime and command rates are bounded. Release hosted robot destroys only that visitor’s resources and prevents pending polls from reconnecting the ended UI. The default free configuration allows one active robot; other visitors receive a capacity message rather than sharing control.

Docker and render.yaml are included. Official pinned assets are fetched at image-build time, followed by a headless native startup check. The optional Netlify build copies frontend assets and generates an API proxy rule from RENDER_BACKEND_URL; it requires Render to allow the exact Netlify origin. Hosted mode supports Browser 3D/map and disables Python image streaming. The normal Windows launcher stays on the local entrypoint.

83 unit checks and 13 local production-entrypoint/native-browser checks passed. The hosted checks cover separate cookies/tokens, actual native motion isolation, task isolation, cross-session token rejection, foreign-origin rejection, capacity messaging, release, capacity reuse and pending-poll behaviour. The native asset/controller/ONNX headless preflight passed. Existing local browser suites are rerun and their results recorded in BUILD_STATUS.json.

Docker is unavailable in this authoring environment: the full image has not been built here. No live Render or Netlify deployment has been made, no free-tier throughput guarantee is given, and actual Netlify proxy cookie forwarding remains to be checked on deployment.
